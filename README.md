# SheetHappens

> **Демо-проект для портфолио.** Сделан, чтобы показать, как я могу собирать Telegram-ботов и мини-CRM на основе Google-таблиц.
> Реального заказчика нет, но всё работает по-настоящему: можно запустить и потыкать.

Telegram-бот для приёма заявок на доставку. Вместо отдельной CRM здесь обычная Google-таблица:
клиент оформляет заявку в боте, а менеджер работает с ней прямо в таблице, как привык.

## От задачи до результата

**Задача.** Небольшая служба доставки принимает заявки в личке и переписывает их в Excel вручную.
Половина данных теряется, клиенты пишут «ну что там с моей посылкой?», а менеджеры путаются, кто чем занят.
Подробности в [ТЗ, нагенеренном Claude'ом](docs/technical-specification.docx)

**Решение.** Бот пошагово собирает заявку и сам кладёт её в таблицу. Через 5 минут он передаёт её менеджеру,
который сейчас на смене и меньше всех загружен. Статусы менеджер ставит в таблице, а клиенту они уходят
только после кнопки «Сохранить и отправить», так что случайный неверный статус до клиента не дойдёт.

**Результат.** Никакой ручной перепечатки. Менеджеры работают в привычной таблице,
клиент сам видит статус своей заявки и получает уведомления. Owner видит общую статистику прямо в боте.

Сам по себе бот довольно простой, интереснее было продумать мелочи. Например, клиент может по-быстрому
удалить ошибочную заявку, и менеджер о ней даже не узнает. А если таблица на минуту отвалилась, бот
не теряет данные и не падает :)

## Возможности

### Клиент

- **Новая заявка** — пошаговый FSM-диалог: тип → подтип → вес → объявленная стоимость → откуда → куда → комментарий → фото → подтверждение
- Типы и подтипы берутся из листа «Справочники» (кэш с TTL, `DICTS_TTL`)
- Кнопки «Назад», «Пропустить», «Отмена», «Начать заново» на каждом шаге
- Валидация веса, стоимости, телефона и длины текста
- **Мои заявки** — последние заявки клиента со статусами
- **Дополнить заявку** — телефон получателя или комментарий (только в статусах «Новая» / «Принята»)
- **Удалить последнюю заявку** — с подтверждением, только в статусе «Новая»
- Уведомление клиенту о смене статуса — только после того, как менеджер нажмёт «Сохранить и отправить уведомления клиентам»

### Уведомления по кнопке

Менеджер меняет «Статус» сколько угодно — клиент ничего не видит. Рассылка уходит только по кнопке:

- лист «Управление», галочка `B1` — бот проверяет её раз в `NOTIFY_INTERVAL` секунд, рассылает изменения и снимает галочку;
- или кнопка/меню «Бот» из [scripts/notify_button.gs](scripts/notify_button.gs) (Расширения → Apps Script → вставить код; кнопка: Вставка → Рисунок → ⋮ → Назначить скрипт `sendNotifications`).

Уведомление получают заявки, у которых «Статус» ≠ «Статус для клиента»; после отправки бот копирует статус в «Статус для клиента». В «Моих заявках» клиент видит именно его.

#### Доставка уведомлений: at-least-once

Есть два способа упорядочить «отправить» и «отметить как отправленное»:

| Порядок | Семантика | Что будет, если бот упал посередине |
|---|---|---|
| сначала отметить, потом отправить | at-most-once | клиент **не получит** уведомление — потеря |
| сначала отправить, потом отметить | at-least-once | клиент получит уведомление **дважды** — дубль |

Здесь выбрано at-least-once: потерянное «ваша посылка доставлена» хуже лишнего сообщения.
Бот сначала шлёт сообщения, а потом одним `update_many` отмечает только успешно отправленные.
Неотправленные (клиент заблокировал бота, Telegram ответил ошибкой) остаются неотмеченными и уйдут при следующем нажатии кнопки.
Exactly-once без идемпотентности на стороне получателя не бывает, а у Telegram её нет.

### Распределение по менеджерам *(сверх ТЗ)*

- Лист «Менеджеры»: имя, Telegram (username без `@`), Telegram ID, график по дням `Пн`…`Вс` в формате `09:00-18:00` (несколько смен через запятую, ночная `22:00-06:00`, пусто — выходной)
- Telegram ID заполняется сам, когда менеджер пишет боту `/start`
- Через `ASSIGN_DELAY` (5 минут) после создания заявка в статусе «Новая» уходит менеджеру на смене с наименьшим числом активных заявок; в таблице заполняются «Менеджер» и «Назначена»
- Задержка даёт клиенту время удалить и пересоздать заявку — удалённая до назначения никому не придёт
- Если на смене никого нет, заявка ждёт, пока кто-то выйдет на смену
- График можно держать в отдельной таблице: `MANAGERS_SPREADSHEET_ID`

### Владелец (owner) *(сверх ТЗ)*

| Команда / кнопка        | Что делает                                                      |
| ----------------------- | --------------------------------------------------------------- |
| `/owner`                | Открыть панель владельца                                        |
| 📊 Статистика           | Всего заявок, клиентов, разбивка по статусам                    |
| 🗂 Последние заявки     | Последние `OWNER_ORDERS_LIMIT` заявок всех клиентов             |
| ♻️ Обновить справочники | Сбросить кэш и перечитать «Справочники»                         |
| 🩺 Проверить таблицу    | Пинг Google Sheets с временем ответа                            |
| `/owner_off`            | Временно выключить owner-режим (видеть бота как обычный клиент) |
| `/owner_on`             | Включить owner-режим обратно                                    |

Владелец определяется по username из `OWNER_USERNAME`. Полностью отключить owner-функции (например, для тестов) — `OWNER_ENABLED=false`.

## Отклонения от ТЗ и почему

| Пункт ТЗ | Как сделано | Почему |
|---|---|---|
| п. 8: автоматическое уведомление клиента о смене статуса (в течение 2 минут) | Рассылка только по кнопке «Сохранить и отправить» | Менеджер может ошибиться со статусом, и клиенту уйдёт неправда. Кнопка даёт проверить перед отправкой. Цена: если менеджер забыл нажать, клиент не узнает. На реальном заказе я бы согласовал это до реализации или сделал гибрид: кнопка для мгновенной отправки плюс автоотправка через N минут |
| — | Распределение по менеджерам, смены, owner-панель | Сверх ТЗ, для демонстрации. На реальном заказе это отдельная оценка и доплата |

## Запуск

### 1. Google-таблица

1. Создайте сервисный аккаунт в Google Cloud, включите Google Sheets API, скачайте ключ в `credits.json`.
2. Создайте таблицу и дайте сервисному аккаунту права редактора.
3. Разметьте листы и заполните справочники:

```bash
python scripts/setup_sheet.py
```

### 2. Переменные окружения

Скопируйте `.env.example` в `.env`:

| Переменная                | Описание                                                         |
| ------------------------- | ---------------------------------------------------------------- |
| `BOT_TOKEN`               | Токен бота от @BotFather                                         |
| `SPREADSHEET_ID`          | ID Google-таблицы                                                |
| `GOOGLE_CREDENTIALS`      | Путь к ключу сервисного аккаунта (по умолчанию `credits.json`)   |
| `OWNER_USERNAME`          | Username владельца без `@`                                       |
| `OWNER_ENABLED`           | `true` / `false` — включить owner-функции                        |
| `PHOTO_CHAT_ID`           | Чат для хранения фото (опционально)                              |
| `DATA_DIR`                | Каталог для рантайм-данных (по умолчанию `data`)                 |
| `DICTS_TTL`               | TTL кэша справочников, сек (300)                                 |
| `NOTIFY_INTERVAL`         | Как часто проверять кнопку рассылки, сек (15)                    |
| `ASSIGN_DELAY`            | Через сколько секунд после создания назначать менеджера (300)    |
| `ASSIGN_INTERVAL`         | Как часто искать заявки для назначения, сек (30)                 |
| `MANAGERS_SPREADSHEET_ID` | Отдельная таблица с листом «Менеджеры» (по умолчанию — основная) |
| `PROXY_URL`               | Прокси для Telegram API (опционально, `socks5://…`)              |
| `LOG_LEVEL`               | Уровень логов (`INFO`)                                           |

### 3. Запуск локально

```bash
pip install -r requirements.txt
python -m app.main
```

### 3'. Запуск в Docker

```bash
docker compose up -d --build
```

Проверить доступ к таблице без бота:

```bash
python scripts/check_repository.py
```

## Безопасность

- Токен бота и ключ сервисного аккаунта — только в `.env` / `credits.json`, оба в `.gitignore`
- Клиент видит и меняет только свои заявки (проверка по Telegram ID)
- Owner-функции доступны только по username из конфига и отключаются флагом
- Ретраи с backoff на 429/5xx от Google API

## Известные ограничения

- **Запускать только один экземпляр бота.** ID заявок выдаются из счётчика в памяти процесса (при старте берётся максимум по листам «Журнал» и «Заявки»). Два процесса с одной таблицей выдадут одинаковые ID.
- **Правка таблицы во время операции бота.** В Google Sheets нет транзакций. Если менеджер удалит или вставит строку на листе «Заявки» в ту же секунду, когда бот меняет или удаляет заявку, бот может попасть не в ту строку. Строки на листе «Заявки» вручную лучше не удалять и не вставлять — для отмены есть статус «Отменена».
- **Лист «Журнал» не очищать.** По нему восстанавливается счётчик ID; без него номера удалённых заявок начнут выдаваться повторно.
- **FSM в памяти.** `MemoryStorage`: после перезапуска у клиентов сбрасываются незавершённые диалоги, недооформленную заявку придётся начать заново. Для демо Redis не нужен, в проде заменяется на `RedisStorage` одной строкой.
